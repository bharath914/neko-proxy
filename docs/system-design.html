A fast, open-source traffic inspector that AI can drive

One Rust core does all the work: proxying, TLS, storage, search, rules. The desktop app is a thin client, and a small debug SDK inside the developer's own Android or iOS app handles phones. Claude and any other MCP client connect to the same core.

Request lifecycle

The data path never waits on the UI or the disk. Persistence and publishing happen after the bytes are already moving.

  1. AcceptListener takes a CONNECT, SOCKS5 or transparent connection.
  2. Intercept TLSMint a leaf cert for the host (cached) and terminate TLS. If the app pins, tunnel it and flag the flow.
  3. Parsehyper and h2 turn bytes into a Flow with an id.
  4. Request rulesBreakpoint, map local or remote, mock, rewrite, in that order.
  5. ForwardConnect upstream through the throttle. Record DNS, connect, TLS and first-byte timings.
  6. Response rulesSame chain on the way back, including response breakpoints.
  7. PersistAsync write: metadata to SQLite, body to the blob store.
  8. PublishSend a delta event to the desktop app, phones and MCP subscribers.

Phone pairing, SDK and certificate setup

The QR payload carries everything the phone needs: { host, port, token, ca_sha256 }. The SDK checks the CA fingerprint it downloads against that value. For anything outside your own app, the core serves a certificate page at http://neko.local with per-platform steps, PEM, DER and Apple profile downloads, and a live trust check. See docs/sdk.md.

Android

  • The SDK pairs by QR and routes the host app's OkHttp traffic through the proxy
  • It trusts the CA at runtime in debug builds, so no network_security_config edit
  • Other apps: the cert page guides the install through system settings
  • VPN mode comes later

iOS

  • The SDK pairs by QR and configures the host app's URLSession through the proxy
  • It trusts the CA for that app only, so no profile install
  • Whole device: the cert page offers the .mobileconfig, then Certificate Trust Settings → full trust
  • The page confirms trust with a real HTTPS call through the proxy

On-device capture (Android VpnService with the core embedded through JNI) comes after the LAN mode ships.

Redaction

Authorization, Cookie, Set-Cookie, API keys and token-shaped values are masked before data leaves the core. Revealing them is an explicit per-session opt-in.

Untrusted content

Response bodies can contain text aimed at the model. Tool results label captured content as data, and write tools never act on instructions found inside it.

Desktop app and mobile SDK

Structure

  • desktop: native Rust (egui), Linux first
  • sdk/android and sdk/ios: debug-only libraries, not apps
  • The core runs as a sidecar process on desktop, started and supervised by the app

Keeping the JVM desktop fast

  • No parsing, decoding or searching in Kotlin. The UI renders what the core sends
  • Lazy list over a paged window of rows, never the full list in memory
  • jpackage with a trimmed runtime and class-data sharing for startup
  • UI sits behind the API, so a native AppKit or GTK shell can replace it later without touching the core

Decisions

Sidecar core, not in-process FFI

Crash isolation, and the desktop app, SDK, CLI and MCP all use one API. No JNI or cinterop layer to maintain for the main path.

WebSocket with protobuf, not gRPC

Easy to speak from Rust, Kotlin and Swift. gRPC adds weight the SDK does not need.

SQLite plus blob files

Queryable metadata with a full-text index, and large bodies kept out of the database so scrolling and search stay fast.

Rules as files

YAML or JSON rules live in git, work in CI, and are easy for AI to write and review.

Read-only AI by default

Inspecting traffic is safe. Changing it needs a human click.

  1. Capture coreHTTP and HTTPS proxy, TLS, store, CLI, HAR export.
  2. Desktop appFlow table, detail viewers, search, filters on macOS first.
  3. Rules and MCPMock, map, breakpoint, throttle. MCP read tools, then approved writes.
  4. Phone pairing and SDKQR flow, Android SDK first, then iOS SDK.
